# Emerging inference research frontiers

**Seven selective bets on *new inference execution or optimization-lifecycle problems*, not seven more ways to subdivide LLM serving.** Updated **2026-11-09** (all seven frontiers reassessed; no extra category). The [eight practical topic areas](../topics/README.md) and their **44 engineering tracks** remain the one canonical bibliography. ## The frontier test

A direction earns a place here when **all three** hold:

1. **New execution or engineering contract:** the workload challenges the request → prefill → autoregressive decode loop, or fundamentally changes how inference kernels/**whole engines** are built, tested and maintained. Generic coding-agent wrappers or ordinary autotuning without a substantive systems mechanism do not qualify.
2. **Evidence appropriate to maturity:** for a brand-new topic, one traceable preprint with a **specific falsifiable system mechanism and limited inspectable pilot/trace/model/proof** is enough to track the question. A public implementation or production signal **raises confidence but is not mandatory**. Distinguish exploratory work, fielded code, hardware simulation and independently replicated results.
3. **An unsettled systems question:** there is a meaningful unresolved scheduling, memory, correctness, communication, throughput, latency **or optimization-budget** question, and a way to test it with real workloads.

**Not frontiers by themselves:** KV caching/offloading/sharing, sparse/hybrid/MLA attention, ordinary MoE/parallelism, P/D disaggregation, quantization, heterogeneous CUDA/ROCm/Ascend porting, and generic semantic response caching. These are **important active engineering tracks** in the topic pages, not new fields. Particularly, *response reuse* is not equivalent to exact *KV reuse*.

| Frontier | Start here | New systems contract / unresolved decision |
|---|---|---|
| **Agent-native inference** | [ThunderAgent](https://proceedings.mlr.press/v306/kang26j.html) (ICML 2026; [code](https://github.com/ThunderAgent-org/ThunderAgent)) | Schedule the **entire agent program**, not isolated token requests. Who owns the long-lived session state, tool sandbox, KV residency and end-to-end critical path? |
| **Real-time omni-modal serving** | [vLLM-Omni Technical Report](https://arxiv.org/abs/2610.09307) (2026 **technical report**; [runtime](https://docs.vllm.ai/projects/vllm-omni/en/latest/)) | Serve asynchronous audio/video/text/action stages with **duplex streaming, backpressure, stage placement and inter-stage transfers**, not one text generation loop. |
| **Diffusion-language-model serving** | [dLLM-Serve](https://doi.org/10.1145/3797905.3800532) (ICS 2026) | Token/step/block-parallel decoding changes compute and memory demand. How should an **iteration-aware, block-aware** scheduler admit, batch and allocate memory versus an AR baseline? |
| **Interactive world-model inference** | [StreamDiffusionV2](https://mlsys.org/virtual/2026/oral/3750) (MLSys 2026; [vLLM-Omni world-model path](https://github.com/vllm-project/vllm-omni)) | An interactive, continuous environment consumes actions and emits frames over many steps. Bound **action-to-first-frame, sustained FPS, jitter, memory growth and state drift** together. |
| **Embodied / VLA action-loop inference** | [Characterizing VLA Models across XPUs](https://proceedings.mlr.press/v306/zhou26e.html) (ICML 2026) | The vision backbone and action expert have dissimilar hardware bottlenecks; meet a **hard perception-to-action deadline** on power-limited heterogeneous edge hardware. |
| **Agentic kernel engineering** | [JustGoal](https://arxiv.org/abs/2610.36434) (2026 preprint; [released kernels](https://github.com/OpenBMB/JustGoal)); compare [KDA](https://nvlabs.github.io/kda/blog/2026-09-27-kda-for-kda/), [CAKE](https://arxiv.org/abs/2608.12629), [KernelBand](https://proceedings.mlr.press/v306/ran26b.html) | When does **goal-only** optimization beat domain-specific agents, and when do compiler IR, model-agnostic diagnostics, reusable search memory or a stronger verification harness justify their cost? Judge **same foundation model, operator shapes, budget, correctness and real serving** rather than cherry-picked per-kernel wins. |
| **Autonomous inference-engine evolution (RSI-adjacent)** | [SEIS](https://arxiv.org/abs/2610.04646) (2026 **preprint**; [code/session artifacts](https://github.com/nehzux/SEIS)) | Optimize **the whole engine**, not just a kernel, through successive agent-led code changes and measured feedback. Can improvements transfer across workloads and optimization sessions without evaluator gaming, correctness regressions or prohibitive search cost? **An evolving engine is not evidence that the agent itself recursively self-improves.** |

**World-model / DiT contextual references (non-canonical).** [BWCache (ICLR 2026)](https://proceedings.iclr.cc/paper_files/paper/2026/hash/ac8ec9b4d94c03f0af8c4fe3d5fad4fd-Abstract-Conference.html) studies Block Feature caching across video denoising steps; [Rolling Forcing (ICLR 2026)](https://proceedings.iclr.cc/paper_files/paper/2026/hash/935151cc6cb5d8b6816133b75233775a-Abstract-Conference.html) changes joint video-frame denoising, context anchoring and model distillation. **November 9 research cross-index (no additional canonical entries):** [ServerBench](https://arxiv.org/abs/2611.06841) evaluates coding-agent-generated *whole serving implementations* using frozen submissions, held-out correctness and stateful replay. [SpecPilot](https://arxiv.org/abs/2611.02501) optimizes specific speculative-decoding engine paths, with Token Forcing to counter benchmark shortcuts. **Neither demonstrates that the optimizer learns a better policy on unseen tasks nor true recursive self-improvement.** [Nebula](https://arxiv.org/abs/2611.09474) and [FlashOffloading](https://arxiv.org/abs/2611.07542) are stronger evidence for *established* agent-oriented KV engineering, not new frontier categories. See the [all-seven-frontier review](../reviews/NOVEMBER_2026_SYSTEMS_SWEEP_20261109.md).

**Further November 9 frontier signals:** [MORTIS](https://arxiv.org/abs/2611.08638) connects typed Agent Program Dataflow with cache residency, prompting a stronger **Harness–Engine State Contract** research question; [Inside the Trap](https://arxiv.org/abs/2611.08902) experimentally isolates durable Agent-prefix cache failure modes, distinct from ordinary LRU hit-rate tuning. [ForgeKernel](https://arxiv.org/abs/2611.04998) demonstrates kernel agent search with profiler-derived mechanism memory including Ascend results, while [The GPU Needs an Operating System](https://arxiv.org/abs/2611.08720) gives a limited real-resident-kernel prototype and explicit missing compiler/OS components. Google announced [TPU Sync and Agent Compute Engine](https://blog.google/innovation-and-ai/infrastructure-and-cloud/global-network/tpu-8i-max-and-8tx/) for cross-tier KV and idle-agent state, but this is **first-party announcement**, not a reproduced/publicly inspected runtime. These are cross-links, not eight new frontier names or second canonical paper rows; [detailed batch evidence](../reviews/NOVEMBER_2026_EXPANDED_SWEEP_20261109.md).

### Autonomous inference-engine evolution: separate engine evolution from RSI

**Scope.** This frontier studies iterative, agent-directed changes to executable inference stacks and to the *process of evaluating those changes*. It is distinct from the **agentic kernel engineering** frontier above: the unit of optimization is an end-to-end engine, workload-specific serving stack or persistent test loop. Calling every optimize–benchmark–repeat loop “recursive self-improvement” overstates the evidence.

- **Engine self-evolution (demonstrated in specific settings):** a largely fixed coding agent improves the *engine artifact* across sessions.
- **Optimizer/agent self-improvement (research question):** experience changes the agent's *future search policy or reusable optimization capability*, improving results on unseen tasks **under equal budgets**; simply reusing better engine code does not establish this.
- **Recursive self-improvement (stronger, unproven here):** the improved system materially enhances its own ability to perform subsequent improvements, producing a verified repeatable feedback loop rather than only a sequence of externally supplied model calls.

| Work / evidence type | Concrete contribution | Boundary that must be preserved |
|---|---|---|
| [SEIS](https://arxiv.org/abs/2610.04646) · 2026 preprint; [author code and histories](https://github.com/nehzux/SEIS) | Iterative sessions inherit mini-SGLang code/reports; evolve kernels, runtime and decoding. Authors report **3.27× throughput vs original mini-SGLang** for **Qwen3-0.6B, H100, single-request** inference. | The **agent stays fixed**; not 3.27× over every production engine/workload. Downstream quality and held-out tests remain necessary. |
| [VibeServe](https://arxiv.org/abs/2605.06068) · 2026 preprint; [code](https://github.com/uw-syfi/vibe-serve) | Outer design search plus inner implementation/correctness/benchmark loop synthesizes bespoke serving stacks. | Author-reported gains emphasize **six non-standard scenarios**; a specialized stack is not evidence of continual adaptation or RSI. **Already canonical** under [Kernels & Compilers](../topics/kernels-compilers.md). |
| [Asari AI](https://asari.ai/blog/inference-optimization) · 2026 **first-party engineering blog** | Reports agent-led changes spanning kernels, schedulers, load balancing and configuration in vLLM on B200. | Author-reported up to **16%** across selected concurrency settings; no independently reproduced, general engine improvement claim. |
| [Together Compiler](https://www.together.ai/blog/together-compiler-continual-compilation-for-ai-inference) · 2026 **first-party technical report/blog** | Persistent engine, hot-swappable forward passes, parallel agents, tiered evaluation and measured parallelism selection reduce optimization-loop overhead. | Its reported **252× is experiment throughput, not inference TPS**; up to **2.6× inference TPS** is a different, configuration-dependent author claim. Production statements are not independent verification. |
| [InferenceBench](https://arxiv.org/abs/2607.20468) · 2026 **benchmark preprint**; [benchmark site](https://inferencebench.ai/) | Fixed-budget, open-ended inference-server optimization exposes weak candidate exploration and experimental decision-making. | Most measured agents lag a simple hyperparameter search, **with a later leading-agent exception on the live leaderboard**; results vary by agent version and baseline. |

**Decisive research test:** does accumulated evidence improve **optimization competence**, or merely the final code artifact? Compare (i) a fresh agent, (ii) a fixed agent inheriting engine code and reports, (iii) an agent reusing a learned/edited optimization strategy, and (iv) a strong conventional tuning/search baseline at matched LLM-token, wall-clock and accelerator budgets. Use the same checkpoint, precision, hardware and request distribution; enforce output/quality oracles and hidden workloads. Report end-to-end goodput/TTFT/TPOT, workload-transfer regressions, **verified improvement per accelerator-hour**, experiment throughput and the full accepted/rejected candidate history. Treat kernel microbenchmarks and hot-reload setup savings as *different metrics* from serving speedup.

**Open failure modes:** agent-generated shortcut code that passes a narrow oracle; numerical/semantic changes in decoding; kernel speedups that disappear on a full engine; overfitting to known shapes or one model; noisy accelerator timings; and an experiment loop whose overhead exceeds the eventual serving gain. **No public work listed here demonstrates open-ended, self-sustaining RSI of an inference optimization agent.** This is a high-priority systems frontier because these claims can be tested, not because RSI is already established.

**November 9 third-pass execution signals** ([source-method audit](../reviews/NOVEMBER_2026_THIRD_PASS_20261109.md)): [Basin](https://arxiv.org/abs/2611.02543) demonstrates actual H200 agent-session admission and decode-memory lending under metastable cache pressure (full predictive controller tested in simulation); [Penelope](https://arxiv.org/abs/2611.00391) challenges prefix-only cache eviction with history-head-first/suffix retention; [Fairway](https://arxiv.org/abs/2611.02082) tests p99 TTFT under cache-hit favoritism; [KVGuard](https://arxiv.org/abs/2611.06138) exposes **request isolation, block lifetime and initialization** as an orthogonal runtime correctness problem. [Serving Agentic Robot Fleets](https://arxiv.org/abs/2611.01404) and [Ripple](https://arxiv.org/abs/2611.01067) emphasize deadline/admission under KV thrashing and shared CPU–GPU contention. [VLA bottleneck characterization](https://arxiv.org/abs/2611.06710) warns of optimizing a weak attention baseline. [UniExit](https://arxiv.org/abs/2611.09159) adds Jetson-device deadline/precision early-exit evidence on a **1B** Transformer with **non-bitwise-matching outputs**, not a general lossless cloud model runtime. These are **cross-links**, not additional canonical rows or new Frontier category counts; device/time/quality caveats remain in the topical source ledger.

### Kernel agents: goal-only vs. KDA vs. compiler-agent co-design

**This is one frontier, not three new categories.** The decisive research question is the *marginal value of agent-specific engineering under controlled compute/model budgets*. Kernel-only optimization belongs here; cross-layer, repeated **engine-level** evolution belongs to the separate frontier above.

| Approach | First-party source / implementation | Mechanism | Valid comparison boundary |
|---|---|---|---|
| **Goal-only (JustGoal)** | [arXiv:2610.36434](https://arxiv.org/abs/2610.36434) · [released B200 kernels](https://github.com/OpenBMB/JustGoal) | General coding agent receives goals and constraints but constructs its own optimizer/evaluator; no prebuilt domain-specific harness | On B200, reported wins versus open-source kernel libraries on 8/10 operators; in a **same-model, single-shape** Fable 5.1 comparison, KDA-0.5 reaches 0.95× of JustGoal. This is not a claim that JustGoal wins across full-shape operator workloads. |
| **KDA / Kernel Design Agents** | [NVIDIA KDA case study](https://nvlabs.github.io/kda/blog/2026-09-27-kda-for-kda/) · [source](https://github.com/NVlabs/kda/tree/260927-kda-for-kda) | Specialized tool/harness, persistent knowledge and correctness feedback; can pair with several Kernel DSLs including CAKE | Reported 2.96× vs FlashKDA on **B300** Kimi Delta Attention; not directly comparable with B200 JustGoal or to full vLLM throughput. KDA reports verifier-overfit candidates it explicitly rejected. |
| **ForgeKernel (OpenBMB; 2026-11 preprint)** | [paper](https://arxiv.org/abs/2611.04998) · [released system/kernels](https://github.com/OpenBMB/ForgeKernel) | Profile hardware behavior of a strong reference, generate an architecture-first curriculum, inherit accepted kernels and probe-grounded knowledge across optimization generations | Real CUDA and Ascend **kernel benchmark** evidence only; compare identical operator/shape/precision/budget with JustGoal/KDA, preserve public vs hidden tests. Repeated kernel artifact improvement ≠ recursive foundation-model improvement. |
| **CAKE (NVIDIA/CMU)** | [arXiv:2608.12629](https://arxiv.org/abs/2608.12629) | Co-design of Agent + typed schedule IR + compiler diagnostics and reusable verifier | Author reports B200 Flash-KMeans and Kimi Delta Attention kernel / serving validation; token budgets, task coverage and availability of the core compiler differ from JustGoal. |
| **CANNBot-CAKE (Ascend; distinct project)** | [arXiv:2610.31034](https://arxiv.org/abs/2610.31034) | CANN-specific multi-DSL generation/evolution with curated knowledge | Reports CANN-Bench hidden correctness on **Ascend 950PR**; not NVIDIA CAKE, not verified on 910B2 and not online vLLM Goodput. |

**Identity resolved (2026-11-04):** [ForgeKernel](https://github.com/OpenBMB/ForgeKernel) has a first-party repository and a distinct **2026-11-03 preprint**, [arXiv:2611.04998](https://arxiv.org/abs/2611.04998). Its key mechanism is a hardware-measured, architecture-first kernel curriculum: accepted generated kernels become the next reference and probe-grounded knowledge persists across runs. **Do not conflate** it with [JustGoal](https://github.com/OpenBMB/JustGoal) (goal-only baseline) or [Kernel Forge](https://arxiv.org/abs/2607.24762) (different paper). The authors report results on NVIDIA Hopper/Blackwell and Ascend 910C/950-series **operator benchmarks**, not vLLM/SGLang end-to-end speedups nor an LLM recursively modifying its own weights. Source-screened Frontier cross-reference only; independently consider G0–G5 before adding a canonical row.

**New benchmark obligation:** add same-model and same-token-budget A/B, hidden distribution and output-equivalence tests, **single shape vs full operator**, compilation/search cost, and engine-level throughput/latency with composed winners. [FastKernels](https://fastkernels.github.io/) highlights that individually faster kernels can fail or regress after composition. A leaderboard score alone is not validated production inference speedup.

The anchors are a **starter reading path, not new canonical admission**. An ICML paper with a kernel benchmark is not evidence of vLLM end-to-end Goodput; a video model demo is not proof of multi-session production serving.

## What remains open (researcher-facing)

| If you work on... | First engineering question | Minimal defensible experiment |
|---|---|---|
| Agent-native inference | What state survives LLM → tool → LLM and who pays for eviction/rebuild? | Multi-turn agent trace; session completion time/P95, cached tokens, GPU idle, tool startup, GPU memory, and interference at equal quality |
| Omni-modal serving | Which stage stalls the live session when frame/audio arrivals become bursty? | Stage-by-stage timeline; P95 event-to-first-output, interruption latency, jitter, backpressure, dropped/late chunks and E2E quality |
| dLLM | Does AR batch/KV scheduling remain optimal when one request emits/updates whole token blocks? | Equal model/quality constraints; memory curve per step, batch efficiency, latency, throughput and output quality against native dLLM runtime |
| Interactive worlds | When must old latent/attention state be refreshed to prevent visual drift? | Long interactive action trace; sustained FPS, action latency P95, memory, consistency/drift checks and controlled action changes |
| VLA execution | Can the compute-bound backbone overlap with the memory-bound action expert within deadline? | Hardware-traced stage latency, missed deadline rate, energy/action and action quality on embedded devices |
| Agentic kernels | Does the generated code remain correct and fast outside public test tensors? | Hidden distributions + precision parity, multi-shape benchmarks, real profiler evidence, compilation cost and downstream serving impact |
| Autonomous engine evolution | Does inherited experience improve the optimizer rather than only the engine checkpoint? | Equal-budget fresh vs. code/report inheritance vs. strategy-memory agent; held-out workloads/models, end-to-end quality/goodput, search cost and regression tracking |

**World-model state-management follow-on (October 2026):** [WorldPager](https://arxiv.org/abs/2610.35529) explores pose-predictable KV-prefetch into NVMe-backed memory for long interactive sessions on a consumer GPU. It is an **adjacent real-hardware experiment**, with int4 quality limitations, and already has its one canonical entry under KV Cache & Context Memory; it is not a seventh frontier or a claim about text LLM KV reuse.

## Watching, not yet promoting

- **Reasoning/test-time-compute control.** [Plan and Budget](https://proceedings.iclr.cc/paper_files/paper/2026/hash/ae8d4084f418bb51575c2ca6c658a05b-Abstract-Conference.html) (ICLR 2026) demonstrates adaptive reasoning budgets, but it is primarily a **model-level quality–compute algorithm**. Promote when a real inference runtime jointly optimizes correctness/quality, token budgets, SLO and co-tenant requests across workloads; avoid mistaking fewer tokens for a proven serving-system breakthrough.
- **RL rollout / online-serving infrastructure convergence.** [Weave](https://www.usenix.org/conference/osdi26/presentation/wu-tianyuan) (OSDI 2026) and [llm-d time-slicing](https://llm-d.ai/blog/rl-post-training-co-operative-time-slicing) provide serious systems evidence for **RL rollout–training job co-scheduling**, not proof of simultaneously protecting **live user-serving SLOs**. Keep as an inference/training crossover watch until that boundary is evaluated.
- **Kernel-agent benchmark trust.** [KernelBench-Verified](https://arxiv.org/abs/2607.16241) (2026 **preprint**) is a high-priority *evaluation check* under agentic kernels, **not** a seventh frontier. Reward hacking, baseline precision and hidden input tests are admission criteria.

## Update rule

**Maintain only 5–7 active frontiers.** To promote an item, document its *new workload/execution contract or system-optimization lifecycle*, a primary **preprint or mature systems paper with inspectable support**, the nearest credible prior baseline or counterexample, and a decisive unresolved bottleneck. Public stack and real hardware strengthen evidence but **do not gate an emerging 2027-oriented research direction**; do not present speculation as validated runtime acceleration. To demote: if vLLM/SGLang/Omni/Dynamo/llm-d ship it as routine infrastructure and newer papers simply improve its policy or kernel, put it back in its existing engineering track. Do **not** add categories or papers here automatically.
